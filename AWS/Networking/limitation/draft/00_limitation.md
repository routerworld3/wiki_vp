Yes. **AWS managed networking exposes fewer routing, traffic manipulation, and troubleshooting controls than traditional routers, firewalls, and application delivery controllers.** Many familiar capabilities require a virtual appliance or a different architecture.

Your examples are useful, but a few need narrower wording.

**Clarifications to your existing list**

| Your observation                                             | Precise AWS limitation                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **ALB/NLB cannot forward using internal DNS across TGW**     | ALB/NLB target groups do not support an arbitrary **FQDN backend target** that they continuously resolve. Reachable private **IP targets** can work across TGW. The limitation is target registration, rather than DNS transport across TGW. [Target types](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/load-balancer-target-groups.html)                                                                                                                   |
| **AWS does not support SNI routing**                         | ALB/NLB support **SNI certificate selection**. However, they do not provide a listener rule that selects different backend pools using TLS ClientHello SNI while preserving TLS passthrough. ALB can terminate TLS and route using HTTP `Host`. [SNI certificates](https://docs.aws.amazon.com/elasticloadbalancing/latest/network/tls-listener-certificates.html), [ALB conditions](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/rule-condition-types.html) |
| **NAT Gateway lacks custom NAT**                             | Correct: it does not expose a traditional policy NAT rulebase for arbitrary SNAT/DNAT, bidirectional static mappings, or inbound port forwarding. [NAT comparison](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-nat-comparison.html)                                                                                                                                                                                                                                        |
| **Managed-device MTU cannot be changed**                     | Generally correct for customer-configured interface MTU on TGW and NAT Gateway. However, this is service-specific: Direct Connect exposes supported MTU choices on virtual interfaces. [TGW MTU](https://docs.aws.amazon.com/vpc/latest/tgw/transit-gateway-quotas.html), [DX interfaces](https://docs.aws.amazon.com/directconnect/latest/UserGuide/WorkingWithVirtualInterfaces.html)                                                                                             |
| **Client IP cannot be preserved across TGW**                 | **TGW itself does not perform NAT.** The restriction applies to **NLB client-IP preservation when its target is reached through TGW**. ALB uses a separate backend connection and conveys the client address through `X-Forwarded-For`; NLB can use Proxy Protocol v2 with compatible targets. [NLB restrictions](https://docs.aws.amazon.com/elasticloadbalancing/latest/network/edit-target-group-attributes.html)                                                                |
| **DXGW/transit VIF cannot use static routing like a router** | Correct for the DX connection: virtual interfaces require BGP. A static route in a TGW route table does not replace BGP on the transit VIF. [DX routing requirements](https://docs.aws.amazon.com/directconnect/latest/UserGuide/WorkingWithVirtualInterfaces.html)                                                                                                                                                                                                                 |

**Additional routing and segmentation limitations**

| Traditional data center capability                                    | AWS managed networking difference                                                                                                                                     | Practical impact or alternative                                                                                                                                                                            |
| --------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1. Policy-based routing by source, port, or application**           | Standard VPC/TGW forwarding uses destination routes. You cannot configure “source A using TCP/443 takes firewall X; TCP/22 takes firewall Y” as a normal route entry. | Separate subnets/attachments and route tables, or use an appliance for policy routing. [Routing](https://docs.aws.amazon.com/vpc/latest/tgw/how-transit-gateways-work.html)                                |
| **2. Separate VRFs for different subnets on one router connection**   | One VPC attachment associates with **one TGW route table**. Traffic entering through that attachment uses that table regardless of its source subnet.                 | A shared VPC attachment cannot select different TGW routing domains per subnet. [Associations](https://docs.aws.amazon.com/vpc/latest/tgw/how-transit-gateways-work.html)                                  |
| **3. Arbitrary ECMP across firewall paths**                           | TGW does not provide ECMP across VPC attachments or ordinary TGW peering attachments, or between different attachment types.                                          | Two firewall VPCs cannot simply be configured as equal-cost next hops for the same default route. [ECMP restrictions](https://docs.aws.amazon.com/vpc/latest/tgw/how-transit-gateways-work.html)           |
| **4. Dynamic routing between peer routers**                           | Ordinary TGW-to-TGW peering uses static routes; it does not exchange routes dynamically.                                                                              | New networks require corresponding peering-route updates or automation. [TGW peering](https://docs.aws.amazon.com/vpc/latest/tgw/tgw-peering.html)                                                         |
| **5. Full routing-policy control**                                    | TGW propagation does not expose traditional per-prefix route maps, and route priority between attachment types is service-defined.                                    | Filter advertisements upstream and design propagation carefully. [Route propagation and priority](https://docs.aws.amazon.com/vpc/latest/tgw/how-transit-gateways-work.html)                               |
| **6. Multiple logical connections from the same VPC to the same TGW** | A TGW cannot have more than one VPC attachment to the same VPC.                                                                                                       | You cannot create separate “inside” and “outside” attachments from one inspection VPC to the same TGW. [Attachment limits](https://docs.aws.amazon.com/vpc/latest/tgw/transit-gateway-quotas.html)         |
| **7. Stretch a subnet across failure domains**                        | A VPC subnet resides entirely within one Availability Zone.                                                                                                           | Multi-AZ applications need separate subnets; they cannot rely on a VLAN/subnet stretched across AZs. [VPC and subnet model](https://docs.aws.amazon.com/vpc/latest/userguide/how-it-works.html)            |
| **8. General-purpose multicast WAN routing**                          | TGW multicast exists, but multicast routing is unsupported over DX, VPN, peering, and Connect attachments.                                                            | An on-premises multicast application cannot simply extend its multicast distribution through DX into TGW. [Multicast restrictions](https://docs.aws.amazon.com/vpc/latest/tgw/tgw-multicast-overview.html) |

**Additional firewall, NAT, and load balancer limitations**

| Traditional capability                                               | AWS managed networking difference                                                                                                     | Practical impact or alternative                                                                                                                                                                                                                                        |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **9. Inspect all traffic through a central firewall**                | VPC route-table insertion cannot steer traffic between hosts in the **same subnet** through a middlebox.                              | Separate workloads into subnets for routed inspection, or use host controls and security groups. [Middlebox restrictions](https://docs.aws.amazon.com/vpc/latest/userguide/route-table-options.html)                                                                   |
| **10. One ordered firewall rulebase with allow and deny**            | Security groups are allow-only; rules from attached groups combine. They lack explicit deny rules and rule ordering.                  | A permissive attached SG cannot be overridden by a restrictive SG. Use NACLs or a firewall where explicit denies are needed. [SG rules](https://docs.aws.amazon.com/vpc/latest/userguide/security-group-rules.html)                                                    |
| **11. FQDN objects in basic network access rules**                   | SG rules accept addresses, CIDRs, prefix lists, and supported SG references—not arbitrary domain names.                               | Domain-based egress policy requires another control such as a proxy or firewall. [SG rule fields](https://docs.aws.amazon.com/vpc/latest/userguide/security-group-rules.html)                                                                                          |
| **12. Backend TLS certificate authentication on the load balancer**  | ALB does **not validate target certificates** for HTTPS target connections.                                                           | Backend encryption does not provide the same certificate identity verification as a proxy configured with a trusted CA and hostname validation. [ALB target TLS](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/load-balancer-target-groups.html) |
| **13. Guaranteed fail-closed load balancing**                        | NLB can **fail open** when all targets are unhealthy, sending traffic to targets regardless of health status.                         | An unhealthy status is not an access-control mechanism. [NLB health behavior](https://docs.aws.amazon.com/elasticloadbalancing/latest/network/target-group-health-checks.html)                                                                                         |
| **14. Transparent hairpin access through the same VIP**              | NLB NAT loopback is unsupported when client-IP preservation is enabled.                                                               | A backend calling its own internal NLB can fail if traffic returns to that backend. [Hairpin restriction](https://docs.aws.amazon.com/elasticloadbalancing/latest/network/edit-target-group-attributes.html)                                                           |
| **15. Carry a public NAT address over private WAN connectivity**     | A public NAT Gateway uses its EIP for internet access through an IGW. Toward TGW/VGW, its source is the NAT Gateway’s **private IP**. | An EIP attached to NAT Gateway does not become the source address seen over DX. [NAT connectivity behavior](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-nat-gateway.html)                                                                                     |
| **16. Treat a NAT Gateway as a firewall interface**                  | You cannot attach a security group to NAT Gateway.                                                                                    | Enforce controls on workloads, subnet NACLs, or a separate firewall. [NAT basics](https://docs.aws.amazon.com/vpc/latest/userguide/nat-gateway-basics.html)                                                                                                            |
| **17. Share every private service endpoint over the routed network** | S3/DynamoDB **gateway endpoints** cannot be consumed through TGW, peering, VPN, or DX from outside their VPC.                         | Gateway endpoints generally belong in each consuming VPC; centralized access requires a supported alternative endpoint design. [Gateway endpoint limitations](https://docs.aws.amazon.com/vpc/latest/privatelink/gateway-endpoints.html)                               |

**Additional troubleshooting and operational limitations**

| Traditional capability                                     | AWS managed networking difference                                                                                                               | Practical consequence                                                                                                                                                                                                           |
| ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **18. Capture packets on every router/firewall interface** | There is no general customer `tcpdump` or SPAN interface inside ALB/NLB, TGW, or DXGW. Flow logs provide metadata rather than packet payloads.  | Capture at accessible endpoints or appliances and correlate with managed-service logs. Flow logs also omit certain traffic. [Flow-log limitations](https://docs.aws.amazon.com/vpc/latest/userguide/flow-logs-limitations.html) |
| **19. Inspect every learned primary and backup route**     | TGW shows the preferred route; a backup can remain hidden until the preferred advertisement disappears.                                         | Absence of a backup route in the displayed table does not necessarily mean the backup was never learned. [Route visibility](https://docs.aws.amazon.com/vpc/latest/tgw/how-transit-gateways-work.html)                          |
| **20. Uniform jumbo-frame and PMTUD behavior**             | TGW supports an 8,500-byte MTU on applicable paths. PMTUD support differs by ingress attachment: supported for VPC/Connect, not DX/VPN/peering. | Jumbo-frame success on one segment does not establish end-to-end support. [MTU and PMTUD](https://docs.aws.amazon.com/vpc/latest/tgw/transit-gateway-quotas.html)                                                               |

For a centralized ingress/inspection architecture, I would put **FQDN backend registration, source-IP handling, policy routing, same-subnet inspection gaps, backend certificate validation, and packet-capture access** at the top of the design checklist. Those tend to change the architecture itself rather than just a configuration setting.
